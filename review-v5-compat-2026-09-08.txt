SECTION A - PROTOCOL CORRECTNESS
================================================================================

A1. DONE *** THE NEGATIVE CACHE RESULT IS NEVER STORED - THIS IS A SPEC "MUST" ***
    Files: Services/BaseBrowsingService.cs (the lookup pipeline)
           Cache/SafeCacheEntry.cs, Cache/BrowsingCacheExtension.cs
    Severity: HIGH.

    The v5 RPC reference is explicit about SearchHashesResponse.cache_duration:

      "The client MUST add this duration to the current time to determine the
       expiration time. The expiration time then applies to every hash prefix
       queried by the client in the request, regardless of how many full hashes
       are returned in the response. Even if the server returns no full hashes
       for a particular hash prefix, this fact MUST also be cached by the
       client."

    So v5 does require a negative cache, keyed by hash prefix - the thing
    SafeCacheEntry models. The lookup pipeline no longer writes one. Verified:
    PutSafeCacheEntryAsync has no callers anywhere outside Cache/ itself, so
    SafeCacheEntry, IsCacheSafeHit, the safe branch of
    BrowsingCacheExtension.LookupAsync and FullHashResponse
    .SafeThreatsExpirationDate are all unreachable.

    Consequence: every URL whose prefix is present in the local database issues
    a hashes.search call on every single lookup, forever. Nothing is amortised.
    A busy caller re-asks the same question thousands of times, which is what
    the MUST exists to prevent, and is the most likely route to having the API
    key throttled.

    NOTE ON WHAT THE FIX IS NOT. The natural-looking fix - "on a safe cache hit,
    return SAFE" - is wrong, and is worse than not caching at all. The safe
    entry is keyed by a PREFIX, and a URL has up to 30 expressions. Returning
    SAFE for the whole URL because one prefix was answered recently means a
    stale entry on a harmless prefix (say "example.com/") suppresses every other
    expression, including "example.com/malware/". That is an unbounded
    fail-open.

    Fix: the negative cache belongs in the SAME role as the local database - a
    reason to drop a prefix from the query set, not a reason to answer. For each
    prefix: if an unexpired unsafe entry matches the full hash, return UNSAFE
    (Local List Mode step 4); otherwise if an unexpired safe entry covers the
    prefix, drop that prefix from the query set and keep going. Only after every
    expression has been considered is SAFE a valid answer.

A2. DONE *** SORTING IS CULTURE-SENSITIVE; REMOVAL INDICES AND THE CHECKSUM BREAK ***
    Files: Databases/MemoryBrowsingDatabase.cs:294 (ModifyThreatListAsync)
           Databases/MemoryBrowsingDatabase.cs:341 (StoreThreatListAsync)
           Databases/MemoryBrowsingDatabase.cs:90  (FindThreatListsAsync)
           Databases/UnmanagedBrowsingDatabaseExtension.cs:92 (checksum)
    Severity: HIGH, on affected locales only.

    List<string>.Sort(), List<string>.BinarySearch(string) and OrderBy(t => t)
    all use Comparer<string>.Default, which is CULTURE-SENSITIVE. The server
    sorts lexicographically by bytes:

      "It is necessary for the server to sort these three hash prefixes
       lexicographically (equivalent to numerical sorting in big endian)."

    Those two orderings are not the same everywhere. Measured, over the hex
    alphabet [0-9A-F]:

      culture   pairwise disagreements   sorted lists equal
      en-US     0                        yes
      tr-TR     0                        yes
      hu-HU     0                        yes
      sv-SE     0                        yes
      da-DK     170                      NO

    Danish collates "AA" as "AA-ring", i.e. after Z. Measured on da-DK:

      List<string>.Sort()       -> 0A000000 AB000000 B0000000 F0000000 AA000000
      ordinal (what Google does)-> 0A000000 AA000000 AB000000 B0000000 F0000000

      Compare("AA000000","F0000000")  default = 1   ordinal = -1

    Two distinct failures follow, both silent:

    (a) REMOVAL INDICES ADDRESS THE WRONG ENTRIES. Partial updates identify
        threats to remove by their zero-based index into the lexicographically
        sorted list. In the sample above "F0000000" is at index 3 locally and
        index 4 on the server, so a removal of index 4 deletes the wrong prefix.
        The local database then silently disagrees with Google about what is
        listed - in the direction of dropping real threats.

    (b) THE CHECKSUM CAN NEVER MATCH. ComputeThreatListChecksumAsync hashes the
        joined list in OrderBy(t => t) order. A different order is a different
        SHA256, so the check at BrowsingDatabaseManager.cs:318 fails, a full
        update is requested, the full update is stored in the same wrong order,
        and it fails again. That is an unbounded full-update loop against the
        API, every cycle, forever.

    The lookup path itself does not break, because Sort() and BinarySearch()
    share the comparer and stay self-consistent. Only agreement WITH THE SERVER
    is lost, which is exactly what indices and checksums depend on.

    Fix: pass StringComparer.Ordinal explicitly at all four sites - Sort(
    StringComparer.Ordinal), BinarySearch(prefix, StringComparer.Ordinal),
    OrderBy(t => t, StringComparer.Ordinal). Better still, store prefixes as
    uint or byte[] and never let string collation into the protocol at all.

A3. DONE Duration nanoseconds are read as milliseconds - a 1,000,000x error.
    File: Clients/Http/DurationConverter.cs:14
    Severity: MEDIUM-HIGH.

        TimeSpan result = new TimeSpan(0, 0, 0, (int)duration.Seconds, duration.Nanos);

    The fifth parameter of that TimeSpan constructor is MILLISECONDS. The proto
    field is NANOSECONDS. Measured, for Duration{seconds=300, nanos=500000000},
    which is 300.5 seconds:

        code produces : 5.18:58:20      (5.79 days)
        correct       : 00:05:00.5      (300.5 s)
        inflated by   : 1,665x

    Both v5 durations pass through this converter, so both are affected:
      - SearchHashesResponse.cache_duration -> a cache entry that should live
        five minutes lives for days, long past the point where Google's answer
        is still true.
      - HashList.minimum_wait_duration -> the client stops updating its database
        for days while believing it is being polite.

    A whole-second duration is unaffected, which is why this has not shown up.
    Nothing in the protocol promises nanos is zero.

    Fix: TimeSpan.FromSeconds(duration.Seconds) + TimeSpan.FromTicks(duration.Nanos / 100).
    Also drop the (int) cast on Seconds, which is an int64 on the wire.

A4. DONE A fabricated version token is sent on the very first synchronization.
    Files: ThreatList.cs:311, Clients/Http/HttpBrowsingClient.cs:333-336
    Severity: MEDIUM.

    A threat list the database has never seen is represented by
    ThreatList.CreateInvalid, whose state is the literal string:

        InvalidThreatListCache.InvalidThreatListState = "AA";

    HttpBrowsingClient sends the state as the version whenever it is non-null:

        if (query.ThreatListState != null) {
            url.QueryParams.Add("version", Convert.ToBase64String(Convert.FromHexString(query.ThreatListState)));
        }

    "AA" is non-null, so a brand new client's first hashLists.batchGet carries
    version=qg== - a version token the server never issued. The initial sync is
    supposed to carry no version at all, which is how the server knows to send a
    full list. Behaviour then depends entirely on the server being tolerant of a
    bogus token. If it ever answers a partial update against it, the client
    applies removal indices to an empty list and stores a fragment.

    Fix: represent "never synchronized" as a null state and let the existing
    null check omit the parameter. If a sentinel is needed internally, it must
    not reach the wire.

A5. DONE Additions longer than four bytes are silently discarded.
    File: Clients/Http/HttpBrowsingClient.cs:397-401
    Severity: MEDIUM.

    Only AdditionsFourBytes is read. The proto also carries:

        additions_eight_bytes    additions_sixteen_bytes    additions_thirty_two_bytes

    and HashListMetadata.HashLength advertises which a list uses
    (FOUR_BYTES, EIGHT_BYTES, SIXTEEN_BYTES, THIRTY_TWO_BYTES). Nothing in the
    project reads HashLength - verified, it appears only in Proto/.

    The four lists in use today are all four-byte, so this is latent rather than
    live. But the failure mode if it ever fires is the worst kind: the entries
    are dropped with no error, the list is quietly short, the checksum then
    fails (A2b), and the client full-updates in a loop.

    Fix: at minimum, throw or raise the synchronization-failed event when a
    non-empty additions field the client cannot handle is present, so an
    unsupported list length is loud rather than silent.

A6. DONE Every threat carrying an attribute is dropped, including FRAME_ONLY.
    File: Clients/Http/HttpBrowsingClient.cs:190
    Severity: MEDIUM.

        if (detail.Attributes.Count > 0) { continue; }

    The two attributes are documented as:

      CANARY     - "Indicates that the threat_type should not be used for
                    enforcement."
      FRAME_ONLY - "Indicates that the threat_type should only be used for
                    enforcement on frames."

    Dropping CANARY is right. Dropping FRAME_ONLY discards a real threat that
    the specification says to enforce, just in a narrower context. A library
    cannot know whether its caller is loading a frame, so deciding for them -
    silently, in the negative - is the one option that is definitely wrong.

    Fix: drop CANARY, and surface FRAME_ONLY on UnsafeThreat so the caller can
    apply it. If it must be dropped for now, do it under an explicit
    `attribute == CANARY || attribute == FRAME_ONLY` test with a comment saying
    so, not a blanket count check that will also swallow attributes Google adds
    later.

A7. DONE The decoder's own hash-prefix serializer is unused.
    Files: Clients/Http/ThreatListUpdateDecoder.cs:150 (DecodeHashPrefixes)
           Clients/Http/HttpBrowsingClient.cs:432
    Severity: LOW - correct today.

    ThreatListUpdateDecoder exposes DecodeHashPrefixes, which serialises each
    decoded value most significant byte first and documents why. It has no
    callers. HttpBrowsingClient instead does its own conversion:

        builder.AddThreatToAdd(entry.ToString("X8"));

    Verified equivalent - for 0x51864045 both produce "51864045", and uppercase
    hex matches what HexadecimalEncode produces for the query side, so the
    endianness is right and prefixes do match. This is a duplication risk, not a
    defect: two encoders for one wire format is how they stop agreeing.

    Fix: call DecodeHashPrefixes, or delete it.

SECTION B - RELIABILITY
================================================================================

B1. Every synchronization failure is swallowed silently.
    File: Services/BrowsingDatabaseManager.cs:284 (also 153, 171)
    Severity: HIGH for operability.

        catch {
            return (null, cDelayToDate);
        }

    No logging, no event, no state change. BrowsingDatabaseManager already
    exposes ThreatListSynchronizationFailed but never raises it for the fetch
    itself. Concretely: an invalid API key returns 400 on every
    hashLists.batchGet, this catch discards it, and the manager retries every 30
    minutes indefinitely. The database never populates and nothing anywhere
    reports a problem.

    This is the condition that makes several findings above reachable, and the
    one that makes them undiagnosable when they are.

    Fix: raise ThreatListSynchronizationFailed here with the exception, and keep
    the retry behaviour exactly as it is.

B2. A request can be sent with size constraints and no list names.
    File: Clients/Http/HttpBrowsingClient.cs:327-330, 369-370
    Severity: LOW.

    Queries naming an unsupported list are skipped by `continue`, but
    sizeConstraints is appended unconditionally afterwards. If every query is
    skipped the request carries constraints and no `names` at all, which the
    server will reject. Short-circuit and return an empty response instead.

B3. sizeConstraints are always sent, even when nothing set them.
    File: Clients/Http/HttpBrowsingClient.cs:345-370
    Severity: LOW.

    When no query carries UpdateConstraints both values stay 0 and are still
    appended. The proto reads 0 as "no limit" so this is harmless, but omitting
    the parameters is closer to the documented intent. Note also the selection
    logic takes the SMALLEST positive value across all queries, which is a
    reasonable reading of a per-request constraint derived from per-list ones,
    but it is a decision worth a comment - a caller who set a large limit on one
    list gets another list's smaller limit applied to theirs.

================================================================================
WHAT IS CORRECT
================================================================================

Worth recording, because these are the parts most likely to be "fixed" by
mistake later:

  - Rice-delta decoding. ThreatListUpdateDecoder is careful, bounds the
    quotient, rejects overflow and trailing data, and treats values as
    big-endian, which the spec confirms: "The big endianness refers to the fact
    that the first byte of the full hash becomes the most significant byte of
    the 32-bit integer."
  - The additions/removals order. Removals are applied to the previous list and
    additions appended afterwards, which is the documented order.
  - Checksum verification and full-update recovery exist and are wired up
    (BrowsingDatabaseManager.cs:316-337), matching "Whenever the checksum does
    not match, the client should perform a full update."
  - minimum_wait_duration handling. An omitted or zero duration leaves
    WaitToDate null or in the past, and ThreatList.Expired then reports true, so
    the client fetches immediately - matching "If omitted or zero, clients
    SHOULD fetch immediately". (Subject to A3 when nanos is non-zero.)
  - Database bootstrap. A descriptor with no stored list becomes an invalid
    ThreatList that reports Expired, so a fresh database does schedule its first
    sync. (Subject to A4.)
  - Batching. The client base64-encodes each prefix and Flurl expands the
    collection into repeated hashPrefixes= parameters; the 1000 cap is enforced.

SUGGESTED ORDER OF WORK
================================================================================
 1. A2 - ordinal comparisons. Silent database corruption, and the fix is
         mechanical and local to four call sites.
 2. B1 - raise the existing event instead of swallowing. Everything else is
         easier to diagnose once this is done.
 3. A1 - restore negative caching, as a prefix-pruning step and NOT as an early
         SAFE return. Re-read the note in A1 before writing it.
 4. A3 - nanoseconds. One line.
 5. A4 - null state for a never-synchronized list.
 6. A6 - distinguish CANARY from FRAME_ONLY.
 7. A5 - make an unhandled additions length loud.
 8. A7, B2, B3 - tidying.
